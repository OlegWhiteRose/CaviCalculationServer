# Лабораторная 4: Авторизация в веб-сервисе и подготовка документации

## Цель работы
- Завершение разработки бэкенда для SPA путем добавления системы аутентификации и авторизации.
- Интеграция Swagger для создания интерактивной документации по API.
- Реализация ролевой модели доступа к методам API.
- Подготовка итоговой технической документации (ТЗ, РПЗ) по проекту.

## Описание задания
1.  **Реализовать авторизацию и регистрацию:**
    - Разработать методы бэкенда для регистрации и аутентификации пользователей.
    - Использовать механизм сессий, хранящихся в Redis, с передачей идентификатора сессии через cookie.
    - Обеспечить автоматическое заполнение поля `создатель` при создании новой заявки аутентифицированным пользователем.

2.  **Реализовать контроль доступа (Permissions):**
    - Настроить проверку прав доступа для методов API в соответствии с ролями пользователей:
      - **Гость (неавторизованный пользователь):** Доступны только методы для чтения данных (GET-запросы списка услуг, одной услуги и т.д.).
      - **Пользователь (создатель заявки):** После аутентификации доступны методы для управления собственными заявками и личным кабинетом.
      - **Модератор:** Доступны все методы API, включая завершение и отклонение заявок других пользователей.

3.  **Интегрировать Swagger:**
    - Добавить описание всех методов API с помощью Swagger (OpenAPI) для создания интерактивной документации.
    - Настроить интерфейс Swagger для возможности выполнения аутентификации и последующих запросов с использованием полученной сессии/токена.

4.  **Создать Sequence-диаграмму:**
    - Разработать диаграмму последовательности, отражающую полный бизнес-процесс взаимодействия с системой через HTTP запросы (без детализации БД и нативного приложения).
    - В качестве `Lifeline` использовать домены (`Пользователь`, `Услуги`, `Заявки`).
    - Сообщения (`Message`) должны соответствовать методам доменов из диаграммы классов (свойство `signature`).
    - В `arguments` сообщений указать ключевые входные и выходные данные.
    - Диаграмма должна включать следующий сценарий:
        - Аутентификация пользователя.
        - Получение списка услуг.
        - GET-запрос пустой иконки корзины.
        - Добавление услуги в заявку-черновик.
        - GET-запрос обновленной иконки корзины.
        - Просмотр черновой заявки.
        - Редактирование полей заявки.
        - Формирование заявки.
        - Получение списка заявок (для создателя).
        - Аутентификация модератора (из второго фронтенда).
        - Завершение заявки модератором.
        - Получение списка заявок (для модератора, с рассчитанными полями).

5.  **Подготовить техническую документацию (ТЗ):**
    - Оформить техническое задание на итоговую систему в соответствии со структурой, приведенной ниже.

## Порядок показа
1.  Продемонстрировать аутентификацию через интерфейс Swagger, открытый в режиме инкогнито. Получить список заявок в Swagger.
2.  Из браузера (вкладка `Application`) скопировать содержимое cookie сессии или JWT из ответа.
3.  В Insomnia/Postman выполнить GET-запрос списка заявок, используя скопированные данные в заголовке `Cookie` или `Authorization`.
4.  Продемонстрировать контроль доступа для списка заявок:
    - Для гостя (без заголовков) — получить ошибку 401/403.
    - Для создателя — получить только его заявки.
5.  Продемонстрировать контроль доступа для метода PUT завершения заявки:
    - Для создателя — получить ошибку 403.
    - Для модератора — получить успешный ответ и показать обновленные поля заявки.
6.  Выполнить GET-запрос списка заявок от имени модератора, чтобы показать, что ему доступны все заявки.
7.  Показать содержимое Redis через `redis-cli` (или другой клиент), продемонстрировать наличие сессий и привязку к пользователям.
8.  Объяснить, как свойство `signature` у сообщений на Sequence-диаграмме в StarUML переиспользовано из диаграммы классов.

### Состав ТЗ (Приложение 1)
-   **Цель:** Описание цели создания системы.
-   **Назначение:** Краткое описание, для чего предназначена система и кто является ее пользователями.
-   **Задачи (12 задач):** Перечень задач, включая 8 лабораторных по бэкенду/фронтенду, разработку нативного приложения, развертывание демо на Pages, подготовку документации и ведение репозитория Git. Для каждой задачи указать используемые технологии.
-   **Функциональные требования (14 подпунктов):**
    -   Список всех HTTP-методов API.
    -   Описание окон (страниц) приложения и доступных на них действий для каждой группы пользователей с указанием вызываемых методов бэкенда.
    -   **Гость:**
        -   Регистрация
        -   Аутентификация
        -   Главная страница
        -   Список услуг
        -   Страница одной услуги
        -   Страницы 403 и 404
    -   **Создатель заявки:**
        -   Страница заявки (черновик)
        -   Список своих заявок
        -   Личный кабинет
    -   **Модератор:**
        -   Список услуг в виде таблицы
        -   Редактирование/создание услуги
-   **Требования к аппаратному обеспечению:** Для сервера и клиента.
-   **Требования к программному обеспечению:** Версии для серверных компонентов и для клиента.
